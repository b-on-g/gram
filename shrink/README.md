# $bog_gram_shrink

Пережатие картинки перед отправкой.

- `fit( width, height, limit )` вписывает размеры в квадрат со стороной `limit`, сохраняя пропорции. То, что уже помещается, остаётся как есть: растянутый кадр только потяжелеет и станет мыльным. Узкая полоска не схлопывается в ноль.
- `image_is( file )` — это картинка, а не документ и не видео.
- `shrink( file )` — готовый к записи в ленд кадр. Зовётся только из фибры.

## Пределы

- Большая сторона до 1600 px. Оригинал с телефона весит мегабайты и в пузыре всё равно показывается мелким, а по сети едет целиком и целиком оседает в памяти мастера.
- Вес до 1,5 МБ. Качество начинается с 0,8 и опускается шагом 0,15 не ниже 0,5: дальше картинка идёт квадратами, и лучше отдать её потяжелее. Когда качество уже на нижнем пределе, сторона ужимается в 0,75 раза. Шесть заходов, дальше отдаётся что вышло.

## Почему так

- Всё пережатие — один промис на вызов. Фибра перезапускается на каждом ожидании, а холст на новом заходе был бы уже другим объектом, то есть другой задачей, и так до бесконечности. Внутри обычный async без фибр.
- Мелкий лёгкий кадр не трогается: перекодирование только испортило бы его.
- Тип результата проверяется всегда: браузер без WebP молча отдаёт PNG, а он тяжелее исходной фотографии. Тогда кодируется JPEG.
- Не дались ни холст, ни кодек — едет оригинал. Это лучше, чем сообщение без картинки.
- Раскодировать сперва пробуем `createImageBitmap`, а не вышло — через `<img>`: Safari показывает HEIC в картинке, но не везде отдаёт его в `createImageBitmap`, и раньше такое фото молча не отправлялось вовсе — промис падал, сообщения не было, ошибки никто не видел. Не раскодировалось никак — едет оригинал без размеров, пузырь тогда квадратный.
- Без перекодирования (`portable`) уезжают только JPEG, PNG, WebP и GIF. Мелкий HEIC прошёл бы как есть и у собеседника в Chrome не показался бы, поэтому он перекодируется всегда, когда браузер его прочитал.
